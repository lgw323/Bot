## 한눈에 보는 결과

기존 Discord 기능과 데이터 형식은 유지하면서, 잘못된 수정이나 실패한 백업 때문에
사용자 데이터가 손상될 가능성을 낮췄습니다. 실제 데이터가 자동 테스트에 섞이지
않도록 분리했고, 백업 파일 전체를 암호화했으며, 손상된 백업은 실제 DB에 적용하기
전에 차단하도록 바꿨습니다.

또한 과거 대용량 파일과 민감한 기록이 남은 Git 이력을 가져오지 않고 코드 저장소를
새로 만들었습니다. 코드는 공개 저장소, 암호화된 운영 데이터는 별도의 비공개
저장소에서 관리합니다. Pi도 새 저장소에서 받은 코드로 교체했으며 현재 정상
실행 중입니다.

## 그대로 유지한 사용자 동작

- 기존 Discord 명령, 버튼 이름과 공개·비공개 응답 방식
- 음악 전용 채널의 주크박스 사용 흐름
- Discord 사용자 기준으로 서버 간 공유되는 즐겨찾기
- 음악 대기열, 반복, 자동 재생과 재시작 상태 형식
- 기존 SQLite 테이블과 저장 데이터 형식
- Watch Together 주소, HTTP·WebSocket 통신 형식, 30초 개설 유예와 5초 퇴장 유예
- 최신 원격 백업 하나를 `db-backup` 브랜치에서 관리하는 방식

## 저장소를 새로 구성한 이유와 결과

기존 Git 이력에는 현재 코드에 필요하지 않은 약 73MB의 대화 원본이 포함돼
있었습니다. 단순히 파일을 현재 폴더에서 지워도 과거 Git 이력에는 남기 때문에,
검증된 현재 코드만 새로운 첫 커밋으로 옮기는 방법을 사용했습니다.

현재 역할은 다음과 같습니다.

| 위치 | 공개 여부 | 포함하는 것 | 포함하지 않는 것 |
| --- | --- | --- | --- |
| [`lgw323/Bot`](https://github.com/lgw323/Bot) `main` | 공개 | 코드, 테스트, 문서, 빈 환경설정 예시 | 실제 `.env`, DB, SQL 백업, 로그, 과거 대화 원본 |
| [`lgw323/Bot-Data`](https://github.com/lgw323/Bot-Data) `db-backup` | 비공개 | 최신 V2 전체 암호화 백업 한 개 | 코드, 평문 DB, 과거 Git 이력 |
| Pi `/home/os/bot` | 서버 내부 | 실행 코드, `.env`, 실제 DB, 최신 백업, 실행 환경과 로그 | 과거 저장소와 구 가상환경 |
| PC 현재 작업 폴더 | PC 내부 | 코드, `.env`, 실제 DB, 최신 백업과 새 가상환경 | 과거 저장소 폴더와 불필요한 캐시 |

확인 당시 코드 저장소에는 `main` 브랜치만 있고, 데이터 저장소에는 독립된
`db-backup` 브랜치만 있습니다. 새 코드 저장소의 Git 이력은 새로운 세 커밋으로
시작하며 전체 Git 객체 묶음은 약 134KiB입니다. 과거 73MB 객체는 새 저장소로
옮기지 않았습니다.

기존 GitHub 저장소, PC의 구 저장소 폴더, Pi의 `/home/os/bot-legacy`와 이전 작업용
임시 폴더는 새 환경 검증 후 삭제했습니다. 현재 저장소의 `.git` 폴더는 새
저장소의 정상 이력이므로 삭제하면 안 됩니다.

## 운영 데이터 이전과 검증

Pi에서 봇의 DB 쓰기를 멈춘 상태로 최신 실제 DB를 보존한 뒤 V2 백업을 만들었습니다.
이 백업을 비공개 데이터 저장소에 올리고, PC에서 다시 내려받아 임시 DB로
복구했습니다.

확인한 결과는 다음과 같습니다.

- 백업 첫 줄: `DISCORDBOT_BACKUP_V2`
- 복구한 SQLite 무결성 검사: `ok`
- Pi 실제 DB와 복구 DB의 주요 테이블별 행 개수: 일치
- 확인한 테이블: 즐겨찾기, 음악 재생 횟수, 음악 설정, 사용자, Watch 세션과 대기열
- PC의 로컬 백업: 비공개 원격 저장소의 최신 파일과 일치

행 개수와 실제 데이터 값은 운영 정보이므로 문서에 기록하지 않습니다.
암호화 키도 바꾸거나 출력하지 않았으며 PC와 Pi의 `.env`에만 유지합니다.

## 실제로 검사한 범위

PC의 새 Python 3.12 가상환경에서 다음을 확인했습니다.

- 자동 테스트 **87개 통과**
- 설치된 패키지 충돌 검사 통과
- Python 코드와 Raspberry Pi용 Bash 스크립트 문법 검사 통과
- Git 공백 오류 검사 통과
- 자동 테스트가 운영 DB와 운영 백업 대신 임시 경로를 사용하는지 확인

Pi에서는 새 가상환경을 만들고 패키지 충돌과 Bash 문법을 검사했습니다. 서비스가
멈춘 상태에서 이전 전체 테스트 84개가 통과했고, 이후 추가된 DB·백업 관련 테스트
20개도 통과했습니다. 서비스 실행 중 전체 테스트를 한 번 더 실행했을 때는 이미
Watch Together가 8000번 포트를 사용 중이어서 서버 테스트 하나만 포트 충돌로
실패했습니다. 현재 코드의 PC 전체 테스트는 87개 모두 통과했으므로 코드 실패로
판정하지 않았지만, Pi에서 전체 테스트를 다시 실행할 때는 서비스를 먼저 멈춰야
합니다.

자동 테스트는 실제 Discord, Gemini, YouTube 또는 GitHub에 요청하지 않습니다.
실제 운영 확인에서는 다음을 별도로 확인했습니다.

- Pi의 `discordbot.service`가 새 코드로 `active` 상태인지
- Discord Gateway 연결과 최근 서비스 오류 여부
- Watch Together의 잘못된 세션 요청이 예상대로 거절되는지
- 실제 V2 백업이 비공개 저장소에 올라가고 다시 복구되는지
- 5분 코드 확인, 매일 `yt-dlp` 갱신, 6시간 백업 cron이 등록돼 있는지

새 공개 저장소의 기준 커밋은 다음 세 개입니다.

1. `3901193` — 검증된 코드와 문서로 새 저장소 이력 생성
2. `a3bb513` — DB 백업을 비공개 저장소로 분리
3. `db9a238` — DB 테스트 환경에도 비공개 백업 주소 격리 적용

PC와 Pi 모두 `db9a238`을 사용하며 공개 원격의 `main`과 일치합니다. 최종 문서
정리 변경은 이 보고서 작성 뒤 별도 커밋으로 남기는 것이 안전합니다.

## 정리 후에도 남은 위험

1. **실행 중인 SQLite 파일 자체는 암호화하지 않습니다.** 원격 백업은 전체
   암호화하지만 Pi의 DB와 `.env`를 함께 가져가는 침해까지 막지는 못합니다.
   SQLCipher 도입은 데이터 형식과 운영 복구에 영향이 큰 별도 작업입니다.
2. **정상 백업이 전혀 없을 때 새 DB로 시작하는 절차가 없습니다.** 현재는 데이터
   유실을 조용히 숨기지 않기 위해 실행을 중단합니다.
3. **생일 기능의 직접 자동 검사가 부족합니다.** 등록, 삭제와 오전 9시 알림은
   다음 관련 수정 전에 현재 동작을 기록하는 테스트가 필요합니다.
4. **Watch Together 초대 링크 자체에는 로그인 제한이 없습니다.** 관리자 종료
   수단은 있지만 링크를 아는 사람의 입장을 미리 차단하지는 않습니다.
5. **Python 3.12에서 `audioop` 지원 종료 경고가 하나 남습니다.** Discord 음악
   재생이 사용하는 라이브러리에서 발생하므로 무작정 제거하지 말고 Python 3.13
   전환을 별도 환경에서 시험해야 합니다.
6. **완전히 같은 설치 환경을 재현하는 잠금 파일은 없습니다.** 직접 의존성 범위는
   관리하지만 PC와 Pi의 모든 하위 패키지 버전을 동일하게 고정하지는 않습니다.

## 문제가 생겼을 때 되돌리는 기준

- 코드 문제: 데이터 저장소는 건드리지 않고 문제를 만든 코드 커밋만 `git revert`
  합니다.
- 새 배포 문제: Pi 서비스를 멈춘 뒤 마지막 정상 코드 커밋과 기존 `.env`, 실제
  DB를 사용해 다시 시작합니다.
- 데이터 문제: 현재 DB를 먼저 별도 복사한 뒤, 비공개 `db-backup`의 V2 백업을
  임시 DB로 복구하고 무결성을 확인한 후에만 운영 DB와 교체합니다.
- 암호화 키 분실: 원격 V2 백업을 복구할 수 없으므로 GitHub가 아닌 별도 안전한
  장소에도 현재 키를 보관해야 합니다.

기존 저장소와 구 폴더는 이미 정리됐으므로 현재의 공개 코드 저장소, 비공개 데이터
저장소, Pi 실제 DB와 암호화 키가 앞으로의 복구 기준입니다.
