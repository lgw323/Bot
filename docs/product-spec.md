# 제품 의도와 유지 계약

이 문서는 DiscordBot을 왜 운영하는지, 사용자가 각 기능에서 무엇을 기대하는지와
명시적인 승인 없이 바꾸면 안 되는 계약을 정의하는 제품 기준 문서입니다.
실행과 테스트 명령은 루트 `README.md`, Raspberry Pi 운영 절차는
`operations.md`, 코딩 에이전트의 작업 방식은 루트 `AGENTS.md`에서 관리합니다.

## 1. 프로젝트 목적과 운영 범위

- 친구들과 게임할 때 사용할 음악 봇에서 시작했습니다.
- 현재 친구 서버 1개와 개인 관리·로그 서버 1개에서 사용합니다.
- 실제 봇은 Raspberry Pi에서 실행하며, Pi에서 코드를 직접 편집하지 않습니다.
- 당장은 소규모 운영이지만 향후 다른 서버로 확장될 가능성은 남겨 둡니다.

## 2. 기능별 사용자 의도와 유지 동작

### 음악

- 목적은 친구들이 게임하거나 대화할 때 음악 전용 채널을 공동 주크박스처럼
  사용하는 것입니다.
- 음악 전용 채널은 대화방이 아니라 주크박스처럼 사용합니다.
- 즐겨찾기는 Discord 사용자 기준이며, 어느 서버에서든 같은 목록을 사용합니다.
- 재시작 직전의 음성 채널, 재생 위치, 현재 곡, 대기열, 반복 모드와 자동 재생
  설정을 복원하는 것이 목표 동작입니다.
- 대기열, 일시정지·재개, 건너뛰기, 셔플, 한 곡·전체 반복과 자동 재생을
  유지합니다. 음악 대시보드와 전용 채널의 메시지 정리 방식도 기능 계약입니다.

### 대화 요약

- 목적은 자리를 비운 친구가 메인 채널의 최근 대화 흐름을 빠르게 파악하도록
  돕는 것입니다.
- 요약은 지정된 채널의 메시지만 수집해 Gemini에 전달합니다.
- 요약 대상 시간과 공개 응답 방식을 포함한 기존 슬래시 명령 동작을 유지합니다.

### 경험치와 랭킹

- 채팅과 음성 채널 활동을 친구 서버의 가벼운 참여 기록으로 사용합니다.
- 기존 글자 길이 계산, 음성 체류 시간 환산, 레벨 요구 경험치 공식과
  `/내정보`, `/랭킹`의 데이터 의미를 유지합니다.
- 향후 다른 서버로 확장할 수 있도록 guild별 데이터 구조를 불필요하게
  단일 서버 전용으로 축소하지 않습니다.

### 생일

- 생일 알림은 친구들이 대화하는 메인 채널에서 사용합니다.
- 생일 알림은 현재 매일 오전 9시를 기준으로 동작합니다.
- 관리자 등록·삭제와 공개 생일 목록의 기존 권한 및 응답 방식을 유지합니다.

### Watch Together

- 목적은 친구들이 Discord 초대 링크를 공유해 별도 계정 없이 같은 YouTube
  영상을 가볍게 동시 시청하는 것입니다.
- 친구들이 초대 링크를 공유해 브라우저에서 입장하는 방식입니다.
- 별도 로그인이나 방장 권한은 현재 없습니다.
- 개설 직후 30초와 마지막 사용자 퇴장 후 5초의 유예 시간을 유지합니다.
- 공유 대기열에는 검증된 YouTube 영상 URL만 추가하며, 브라우저에 표시하는
  제목·추가자·채팅 입력은 HTML로 실행되지 않도록 처리합니다.
- 세션이 생성되면 개인 로그 채널에 최고관리자 전용 강제 종료 버튼이 나타납니다.
  버튼은 접속자를 끊고 초대 메시지, 세션과 공유 대기열을 함께 정리합니다.
- 봇 재시작 뒤 접속자가 없는 이전 세션은 한 번 정리합니다. 별도 로그인이나
  초대 링크 자체의 접근 제한은 아직 없습니다.
- 웹 화면은 영상 감상과 협업 정보를 우선하는 현대적인 어두운 웹
  애플리케이션으로 구성합니다. 주황색은 현재 재생, 선택과 주요 행동에만
  사용하고, 장식용 상태 정보·격자·스캔선·지속 애니메이션은 사용하지 않습니다.

### 관리자 로그

- 로컬 운영 로그와 개인 관리 Discord 서버를 오류 확인 창구로 사용합니다.
- 다른 라이브러리의 로그 handler를 임의로 제거하지 않고, Discord 재연결 때
  원격 handler를 중복 추가하지 않습니다.
- Watch Together 강제 종료 제어는 개인 관리 서버의 최고관리자만 사용할 수
  있어야 합니다.

## 3. 큰 구성요소와 책임

| 구성요소 | 책임 |
| --- | --- |
| `main_bot.py` | 환경 설정을 읽고 Discord 봇과 기능 모듈을 시작 |
| `database_manager.py` | SQLite 연결, 스키마, 기능별 데이터와 SQL 백업·복구 |
| `cogs/music/` | Discord 음악 요청, 실제 재생, 버튼 UI와 재시작 상태 |
| `cogs/summary/` | 메시지 수집과 Gemini 요약 |
| `cogs/leveling/`, `cogs/birthday/` | 활동 경험치와 생일 관리 |
| `cogs/watch_together/` | Discord 초대, HTTP·WebSocket 서버와 웹 화면 |
| `cogs/logging/` | 로컬·Discord 오류 로그와 관리자 제어 화면 |
| `scripts/` | Pi 코드 업데이트와 DB 백업 자동화 |

`main_bot.py`는 프로그램 시작만 담당하고 새로운 기능 처리는 각 `cogs/` 아래에
두는 방향을 유지합니다. DB 복구와 스키마 준비가 끝난 뒤 FastAPI와 Cog를
시작하여 외부 요청이나 기능 이벤트가 준비되지 않은 DB에 접근하지 않게 합니다.
DB 연결과 저장은 현재 `database_manager.py`에
집중되어 있으며, 향후 내부 분리 시에도 기존 공개 함수와 데이터 형식은 유지합니다.
DB 연결 설정은 봇 전용 연결 함수에서만 적용하며 Python 표준 `sqlite3.connect`를
전역으로 변경하지 않습니다. 시작 시 원격 백업 조회, SQL 복구와 스키마 준비는
서로 분리된 단계로 실행됩니다.

음악 재시작 상태는 `music_state_store.py`가 기존 JSON 형식 그대로 저장·로드하고,
`music_session_restorer.py`가 읽은 값을 Discord 채널과 재생 대기열에 적용합니다.
저장 중 오류가 나면 마지막 정상 상태 파일을 유지하며, 정상적으로 읽은 상태 파일은
기존과 같이 한 번만 사용한 뒤 삭제합니다.
종료 시 활성 음악 세션이 없다면 이전의 정상 스냅샷은 제거하지만, 손상된 JSON은
원인 확인을 위해 보존합니다.

## 4. 데이터와 백업의 현재 상태

### 저장소 분리

- 공개 코드 저장소는 [`lgw323/Bot`](https://github.com/lgw323/Bot)이며
  `main` 브랜치에 코드, 테스트와 문서만 둡니다.
- 운영 백업 저장소는 비공개 [`lgw323/Bot-Data`](https://github.com/lgw323/Bot-Data)이며
  코드 이력과 독립된 `db-backup` 브랜치에 최신 암호화 백업 한 개만 둡니다.
- 공개 코드 저장소에는 `db-backup` 브랜치를 만들지 않습니다.
- 실제 저장소 주소는 각 실행 환경의 `.env`에 있는 `DB_BACKUP_REMOTE_URL`로
  지정합니다. 이 값이 없으면 공개 `origin`으로 우회하지 않습니다.

### 운영 데이터

- SQLite DB: `data/bot_database.db`
- 재시작용 음악 상태: `data/music_state.json`
- SQL 백업: `data/database_backup.sql`
- Pi 로컬 보관: `data/archives/` 최근 7일
- 원격 보관: `DB_BACKUP_REMOTE_URL`로 지정한 별도 비공개 저장소의
  `db-backup` 브랜치

### 암호화 범위

- 새 백업은 SQL 원문 전체를 Fernet으로 암호화합니다. 사용자·서버 ID, 생일,
  Watch Together 세션, 음악 URL·제목과 테이블 구조가 모두 보호됩니다.
- 운영 중인 `data/bot_database.db` 자체는 암호화하지 않습니다. Pi의 DB 파일과
  `.env`를 함께 가져갈 수 있는 침해까지 막는 구조는 아닙니다.
- 새 백업에는 형식 버전 표식을 붙이며, 기존의 필드 암호화 SQL 백업도 계속
  복구할 수 있습니다.
- `DB_ENCRYPTION_KEY`가 없거나 형식이 잘못되면 새 SQL 백업 생성을 중단하여
  어떤 운영 데이터도 평문 백업에 들어가지 않게 합니다.

### 빈 데이터와 복구

- DB와 로컬 SQL 백업이 모두 없으면 `DB_BACKUP_REMOTE_URL`의 비공개
  `db-backup` 브랜치에서 복구를 시도합니다.
- `DB_BACKUP_REMOTE_URL`이 없으면 공개 코드 저장소로 우회하지 않고 실행을
  중단합니다.
- 원격 복구까지 실패하면 현재는 빈 DB를 만들지 않고 실행을 중단합니다.
- 내려받은 SQL은 별도의 임시 DB에 먼저 적용해 봅니다. 끝까지 정상 적용된 경우에만
  운영 DB 위치로 옮기므로, 손상된 SQL이 기존 DB를 중간 상태로 덮어쓰지 않습니다.
- 암호화된 값이 있는데 키가 없거나 다른 키라서 읽을 수 없으면 암호문을 정상
  데이터처럼 저장하지 않고 복구를 중단합니다. 과거 평문 백업은 계속 읽을 수
  있도록 구분합니다.
- 원격에도 백업이 없는 것이 확인되면 새 DB로 시작하는 방향이 논의됐지만, 안전한
  확인 절차는 아직 구현되지 않았습니다.
- 로컬 SQL 덤프는 권한이 제한된 임시 파일에서 문법과 트랜잭션을 확인한 뒤 전체
  암호화합니다. 암호화 왕복 검사까지 통과한 경우에만 마지막 정상 백업과
  교체하며, 임시 평문은 항상 삭제합니다.
- 자동 백업은 1KB보다 작은 SQL 파일의 원격 업로드를 차단합니다.
- 자동 백업은 SQL 생성, Pi 로컬 보관 또는 원격 `db-backup` 업로드 중 하나라도
  실패하면 실패 상태로 끝나며 `backup.log`에 원인을 남깁니다. 이전 백업을 새
  백업인 것처럼 다시 올리지 않습니다.

## 5. 유지해야 할 데이터·화면 계약

명시적인 기능 변경이 아니라면 다음 형식을 유지합니다.

- Discord 슬래시 명령어 이름과 사용자 응답 방식
- SQLite 테이블과 기존 데이터의 의미
- 버전 표식이 있는 전체 암호화 백업과 기존 SQL 복구 호환성
- `data/music_state.json`의 필드와 복원 순서
- Watch Together URL, HTTP endpoint와 WebSocket 메시지 형식
- 음악 전용 채널의 기존 대시보드와 메시지 정리 방식
- 사용자에게 보이는 기존 명령 이름, 응답 문구와 공개·비공개 응답 방식

SQLite의 WAL 모드는 DB 초기화 시 적용하며, 각 연결에는 `synchronous=NORMAL`,
`temp_store=MEMORY`, `cache_size=-2000` 설정이 적용됩니다.

## 6. 의도적으로 아직 제공하지 않는 것

- Watch Together의 별도 계정, 방장 권한과 초대 링크 접근 제한
- 정상 원격 백업이 전혀 없을 때의 무조건적인 빈 DB 생성
- 운영 SQLite 파일 자체의 암호화
- 모든 하위 Python 패키지의 완전한 잠금 파일

이 항목은 누락된 구현을 의미하지 않습니다. 도입 여부와 기존 사용자 흐름에
미치는 영향을 먼저 결정해야 하는 제품 판단 사항입니다.

## 7. 확인된 후속 판단 사항

1. 정상 원격 백업이 없을 때 새 DB 생성을 허용하는 확인 절차
2. 현재 최소 버전 중심인 일반 의존성을 정확한 버전 잠금 파일로 관리할지 여부
3. 패키지 환경까지 완전히 원자적으로 교체·복구하는 배포 구조
4. Watch Together 초대 링크 자체의 로그인 또는 접근 제한
5. 운영 SQLite 파일 자체를 SQLCipher 등으로 암호화할지 여부
6. Python 3.13 전환 전 음악 재생·TTS·음성 라이브러리 호환성 검증

자동 업데이트는 현재 일반 의존성과 `yt-dlp` 정책을 분리했습니다. 코드 변경 시
일반 의존성을 `-U` 없이 먼저 준비하며, 일일 작업은 `yt-dlp`만 최신화합니다.
실패하면 재시작하지 않고 다음 cron 주기에 재시도하며, 새 코드 재시작 실패 시 직전
커밋으로 한 번 복구합니다. 다만 같은 `bot_env`에 패키지를 설치하므로 설치 도중의
Python 환경까지 완전히 원자적으로 되돌리는 구조는 아닙니다.
새 코드가 정상 기동한 뒤에는 사용 종료된 음성 수신·음성인식·옛 검색·구형 Gemini
직접 패키지를 제거합니다.

음악의 장기 재생·자동재생·UI 작업은 상태 정리 시 취소 완료까지 기다립니다. Cog
종료 중에는 새 UI 작업을 만들지 않습니다. 요약 메시지 정리 작업은 객체 생성만으로
시작하지 않고 Discord가 Cog를 로드할 때 시작하며, 언로드할 때 취소합니다.
