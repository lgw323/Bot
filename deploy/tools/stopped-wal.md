# Stopped-cutover WAL helper: local preparation only

This retained design describes the October 15 preparation boundary. The published
local model and its current test commands are described in
[local tooling](../../docs/local-tooling.md). Historical candidate references below
are not current deployment targets or authorization to execute a host cutover.

`stopped_wal.py` is an auxiliary callable, with no CLI, production observer,
runtime hook, service action or pointer action. Only explicitly supplied synthetic
temporary targets have been exercised. This is not authorization to run on the Pi.

The existing `LocalDeployment.activate` performs final stopped backup, writes
`activation.json`, then changes the current release pointer. Existing recovery
promotion copies exact reviewed candidate bytes; its accepted self-contained
DELETE restore format remains unchanged. Do not implement another restore, backup
format, deploy pipeline or automatic journal switch at application startup.

## Interface and ownership

`OperationOwner` acquires the existing kernel-lock implementation, checks the lock
inode, and requires `StopEvidence` for the exact target/lock, stable ownership
epoch, unexpired lease, both services and exclusion of every consumer. It checks
that evidence at admission, after preservation, before journal transition and
before success. Missing/inactive ownership or unknown/active service state fails.

The `observe(target, deadline)` callback is a **trusted supervisor integration
contract**, not evidence generated by this helper. There is no production adapter
in this preparation. The synthetic tests model these observations; only kernel
lock contention and SQLite behavior are actual OS operations. A caller-supplied
boolean must not become the production proof of exclusion. The future bounded
supervisor must prevent unrelated starts and new DB opens for the entire handover,
not merely enumerate existing PIDs once. No local test establishes that on the Pi.

The current deployment pipeline already owns its lock. Do not nest this context
inside it or release its lock to use this helper. A separately reviewed controller
integration must use one owner from stop through final backup and pointer change,
and must intercept unverified normalization outcomes before the current automatic
rollback/start path. Neither that controller nor an authentication broker was
implemented here. Supper, Moving, Cloudflare and other services are out of scope.

## Data preservation and operation

- Refuse missing/non-regular/linked/aliased inputs, existing output paths,
  mismatched restore hash, rollback journal, DELETE with sidecars, missing lock,
  unavailable ownership observations, and incomplete/expired ownership evidence.
- Save original main/WAL/SHM bytes under a new private directory before **any**
  writable target connection. Verify hashes, source stability and directory sync.
  Originals and partial evidence are retained on failure. These raw forensic
  copies are not automatically selected as a recovery DB or promoted anywhere.
- Validate the supplied DELETE restore through an immutable read connection.
  Validate the latest target separately, require schema/ledger/integrity and full
  data/metadata/count equivalence. A stale final backup causes refusal; the helper
  never replaces newer writes with it. Writable validation/close may itself let
  SQLite checkpoint/remove sidecars; the receipt marks that boundary first.
- Close validation connections, open a dedicated autocommit `mode=rw` connection,
  execute `PRAGMA journal_mode=WAL`, require `wal`, then execute
  `PRAGMA wal_checkpoint(TRUNCATE)` and require `(0,0,0)`. Close the connection.
  No `unlink`, `remove`, `replace`, source rename or sidecar deletion is performed.
- Revalidate integrity/semantics, same inode, WAL header, absent sidecars and exact
  unchanged DELETE restore artifact. All file writes are confined to requested
  originals/receipt or SQLite's own files. No SQL data updates/migrations occur.

File absence and a complete checkpoint do not prove exclusive access. An idle
connection or a future external opener may escape SQLite-level detection. The
supervisor exclusion contract is mandatory. WAL does not cure every BUSY cause,
clear a running readiness hard latch, establish capacity, or prove host health.

## Failure and receipt meaning

`NormalizationFailed.receipt` carries stage, error type/SQLite code, before/after
file identities/hashes/header, any known semantic comparison and whether a failure
receipt was persisted. No DB values or credentials are logged. Once any writable
target access was attempted, failure means `failed_after_target_access`, even if
observed hashes are equal. A later exception can leave the DB already in WAL mode.

On receipt-write/close failure, disk may contain only earlier lines, even a
`complete` line. A line alone does not admit cutover: require a successful bounded
controller/function result and continuing ownership. Missing/corrupt receipts,
process termination, or unavailable after-state are uncertain outcomes. Keep the
pair stopped and preserve the latest DB plus all originals. Reconcile mode,
integrity and semantics before deciding the next action. Never blindly retry,
delete sidecars, switch back to DELETE or restore an older backup.

The helper's SQLite progress deadline and 100ms busy timeout do not bound every
filesystem operation or an arbitrary callback. A hard deadline belongs to the
future supervisor. Interrupted before/after images do not establish crash/power-loss
recovery. Linux ownership/permissions/fsync behavior needs installed validation.

For a separately approved explicit restore promotion, retain the original DELETE
candidate and reviewed source hash. This helper does not perform that promotion or
silently transform its input; that path requires its own reviewed integration.
